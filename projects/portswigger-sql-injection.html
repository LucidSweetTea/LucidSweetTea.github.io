PortSwigger Web Security Academy: SQL Injection Practitioner

Web Application Security • SQL Injection • Burp Suite • Authorized Lab Environment

Project Overview

This project documents hands-on SQL injection testing completed through PortSwigger Web Security Academy in intentionally vulnerable and authorized lab environments.

The work progressed from basic SQL injection discovery through more advanced techniques including UNION-based data retrieval, authentication bypass, blind inference, error-based extraction, time-delay attacks, and filter bypass through XML encoding.

All testing was performed against PortSwigger Web Security Academy labs. Credentials, session cookies, active lab URLs, and other temporary sensitive values are intentionally excluded from this portfolio.

Assessment Methodology

  1. Identified application-controlled parameters that influenced back-end SQL queries.
  2. Submitted controlled test values and compared response content, status codes, errors, and timing behavior.
  3. Determined query structure, including the number of returned columns and compatible data types.
  4. Used UNION-based techniques to retrieve information from additional database tables.
  5. Tested blind injection conditions where query results were not directly returned to the browser.
  6. Automated repetitive inference testing with Burp Intruder when manual testing was inefficient.
  7. Applied encoding techniques when a web application firewall blocked obvious SQL injection syntax.
  8. Validated successful exploitation by completing the objectives of each authorized lab.

Techniques Practiced

1. SQL Injection Detection

Tested application parameters for unexpected SQL evaluation by modifying inputs and observing changes in application behavior. This included syntax testing, mathematical expressions, and controlled query manipulation.

2. UNION-Based SQL Injection

Determined the number of columns returned by vulnerable queries and identified columns capable of returning text. UNION queries were then used to retrieve controlled database information from additional tables.

3. Authentication Logic Bypass

Explored how unsafe SQL query construction can allow attacker-controlled input to alter authentication logic and bypass intended account validation.

4. Blind SQL Injection with Conditional Responses

When database results were not directly returned, boolean conditions were tested by comparing observable application responses. Burp Intruder was used to automate repeated character testing.

5. Error-Based SQL Injection

Used database error behavior as an information channel. Controlled type conversion and query errors demonstrated how verbose database messages can unintentionally expose sensitive query results.

6. Time-Based Blind SQL Injection

Tested boolean conditions by triggering controlled database delays. A true condition produced a measurable delay while a false condition returned normally.

Burp Intruder was configured to issue requests sequentially so response timing could be compared reliably while testing individual password positions.

7. XML Encoding and WAF Bypass

Identified a SQL injection flaw in an XML-based stock-check request. An obvious UNION payload was blocked by the application's filtering layer.

Using the Hackvertor extension, the SQL input was represented with XML entities. The application decoded the XML before processing the query while the filtering layer failed to recognize the encoded SQL syntax.

After bypassing the filter, a single-column UNION query concatenated usernames and passwords into one returned value, demonstrating how encoding inconsistencies between security controls and application parsers can create exploitable gaps.

Blind SQL Injection Workflow

One of the most useful lessons from the learning path was understanding how information can still be recovered when an application displays no database results.

In the time-based labs, the testing model was:

  • True condition: trigger a controlled database delay.
  • False condition: return without the delay.
  • Compare response timing to infer whether each tested condition was true.
  • Repeat the process for individual positions when extracting an unknown value.

This demonstrated that the absence of visible output does not necessarily prevent data inference when other side channels are available.

Filter Bypass Analysis

The XML stock-check lab demonstrated an important defensive lesson: a WAF and the protected application may interpret the same input differently.

A plainly written UNION query was detected and blocked. After the input was represented using XML entities, the filtering layer allowed the request, while the application later decoded and evaluated the SQL expression.

This reinforced the importance of preventing SQL injection at the database interaction layer rather than relying exclusively on pattern-based filtering or request inspection.

OAST Concepts Reviewed

The learning path also introduced out-of-band application security testing concepts, where a vulnerable database can be induced to make an external DNS or HTTP request.

Security Impact

SQL injection can allow an attacker to interfere with database queries and, depending on application architecture and database permissions, may lead to:

  • Unauthorized access to sensitive database information
  • Authentication bypass
  • Exposure of usernames, password data, and application records
  • Modification or deletion of stored information
  • Privilege escalation within an application
  • Out-of-band data exfiltration in certain environments

Remediation Recommendations

  • Use parameterized queries or prepared statements instead of concatenating untrusted input into SQL statements.
  • Apply strict server-side input validation appropriate to the expected data type and business function.
  • Use least-privilege database accounts so application queries have only the permissions they require.
  • Avoid exposing verbose database error messages to users.
  • Normalize and validate encoded input before security inspection so filtering controls and the application interpret requests consistently.
  • Treat WAF rules as defense-in-depth rather than as the primary control for preventing SQL injection.
  • Monitor unusual database behavior, repeated malformed requests, and abnormal response timing patterns.

Key Takeaways

This project strengthened my understanding of SQL injection beyond basic syntax testing. Different application behaviors can provide different information channels, including returned content, conditional responses, database errors, and measurable timing differences.

The labs also demonstrated why strong application-layer defenses must focus on safe database interaction. Encoding tricks and parser differences can bypass superficial filtering, while parameterized queries prevent attacker-controlled input from becoming executable SQL.
